## Motion: broad integrated candidate, subject to host proof

Physics springs use `stiffness`, `damping` and `mass`, incorporating existing gesture/animation velocity. Duration-plus-bounce springs do **not** carry velocity. Mixing those controls can silently change the model: physics parameters override bounce/duration. The workshop should distinguish a physical live spring from a sampled CSS easing. Inertia supports bounds and `modifyTarget` for snapping. These are documented contracts that still need interruption/release traces in the installed version. [Transition reference](https://motion.dev/docs/react-transitions).

`useSpring(sourceMotionValue)` follows changing source values; `.set()` retargets, `.jump()` updates immediately. That supports a reactive pointer/scroll follower without a React render per frame. A graph/control that only runs one prerecorded animation does not prove this requirement. [useSpring](https://motion.dev/docs/react-use-spring).

For a framework-independent numeric adapter, prefer evaluating the public **`springValue(initialOrSource, options)`** export from `motion` before composing `motionValue` with repeated generic `animate()` calls. It accepts a number/unit string or a source motion value; `.set()` retargets the follower. Physics options carry velocity. The installed 14.7.1 `follow.mjs` steers the active `FollowAnimation` through `setTarget`, using its analytical velocity, rather than requiring the adapter to reconstruct an animation for every target change. That gives the narrow core a specific continuity mechanism to test. On teardown, release the adapter's change subscription and destroy its owned follower; detach source-follow work and avoid destroying a shared source owned by the caller. Verify cancellation/reset on native close separately from permanent destruction on unmount. Measure this import graph separately from generic animation and React layout features: a smaller surface is a hypothesis until bundled. [Official springValue contract](https://motion.dev/docs/spring-value), [published follow implementation](https://unpkg.com/motion-dom@14.7.1/dist/es/value/utils/follow.mjs).

`layout` measures size/position changes caused by React rendering and projects them with transforms; layout state belongs in `style`/`className`, not simultaneous `animate` targets. Children, borders, text and shadows can stretch, with correction depending on structure/style; `layout="position"` is sometimes preferable. Horizontal window resizing deliberately blocks layout animations; SVG layout is unsupported. Test content expansion and actual list reorder, with final normal-flow boxes, rather than translate-only demos. [Layout guide](https://motion.dev/docs/react-layout-animations).

Current Motion documentation describes `Reorder` for both lists **and grids**, with automatic dimension detection. Do not carry forward older blanket claims that it only supports a one-dimensional list. Its callbacks still must update application order. Built-in drag supplies momentum and elastic constraints but is not native HTML dropzone behavior. Keyboard reorder/drag alternatives remain application work. [Reorder](https://motion.dev/docs/react-reorder), [drag](https://motion.dev/docs/react-drag).

**Selection gap: Motion layout retargeting does not meet strict retained vector momentum.** In the published 14.7.1 projection node, `startAnimation()` calls `motionValue.jump(0, false)` and starts a new `[0, 1000]` progress animation with `velocity: 0`. Reprojecting from current visible geometry can preserve position while resetting the rate of change; that is not the same as carrying old x/y/size velocity into the next target. The framework-independent `animateLayout` path uses the same projection node. This limits the integrated layout approach even though the separate `springValue` numeric core has velocity-aware retargeting. The real-host proof must sample layout velocity, not merely inspect continuous boxes. [Exact projection module](https://unpkg.com/motion-dom@14.7.1/dist/es/projection/node/create-projection-node.mjs), [animateLayout module](https://unpkg.com/motion-dom@14.7.1/dist/es/layout/animate-layout.mjs).

`motion.create(Component)` needs a forwarded native ref; create wrappers outside rendering. SSR writes initial styles and offers `motion/react-client` for React Server Component usage. None of that proves Radiant's actual button/details/dialog ref forwarding, native default actions, event composition or top-layer behavior. [Motion component reference](https://motion.dev/docs/react-motion-component).

`MotionConfig` defaults to reduced motion **never**. Set `reducedMotion="user"`: documented behavior disables transform/layout while allowing opacity/color animation. Independently driven values and semantic changes need explicit policy and live-preference testing; do not assume the provider makes every custom animation accessible. [MotionConfig](https://motion.dev/docs/react-motion-config), [accessibility](https://motion.dev/docs/react-accessibility).

The official loading seam is `m` plus `LazyMotion`; **`domMax`** adds drag/layout that `domAnimation` lacks. A dynamically imported feature bundle can defer that work. The guide's size numbers are examples, not Radiant measurements. Mini WAAPI APIs alone are not an equivalent substitute for the integrated feature set. [Bundle guide](https://motion.dev/docs/react-reduce-bundle-size).

## React Spring: credible spring core; layout and gesture assembly cost

React Spring exposes physical mass/tension/friction, velocity, rest criteria, clamp and independent per-property configuration. Duration/easing is a separate path. [Spring configuration](https://www.react-spring.dev/docs/advanced/config).

Versioned implementation supports a narrower, inspectable interruption claim: `SpringValue.advance()` reuses `lastVelocity` for physical integration; `_start()` uses current positions; `AnimatedValue.reset()` clears velocity only if that node was already done. Retargeting a running numeric spring therefore has an explicit continuity mechanism. Calling reset/from/set/immediate can change this behavior: prove the chosen adapter rather than asserting all API calls preserve momentum. Fluid goals are observed, and `.to()` supports derived reactive values. [SpringValue 10.1.2 source](https://github.com/pmndrs/react-spring/blob/v10.1.2/packages/core/src/SpringValue.ts), [AnimatedValue source](https://github.com/pmndrs/react-spring/blob/v10.1.2/packages/animated/src/AnimatedValue.ts), [interpolation](https://www.react-spring.dev/docs/advanced/interpolation).

`useResize` observes container/window width and height and returns spring values. That is useful measurement, but it does not establish a full automatic projection engine for arbitrary layout/reparent/reorder changes. The shortlist found no equivalent documented `layout` primitive: treat a measurement/FLIP/reorder adapter as Radiant-owned work unless the browser proof demonstrates an upstream alternative. [useResize](https://www.react-spring.dev/docs/utilities/use-resize).

Use Gesture supplies input state rather than animation. Its canonical example makes movement immediate while dragging, then springs to origin; it does not by itself prove velocity-aware release, arbitrary snap or layout reorder. Those need explicit adapter logic and signed release velocity. [Official introduction](https://use-gesture.netlify.app/docs/).

React Spring's isomorphic layout hook uses effect behavior on the server and layout effect in the browser. Its reduced-motion helper controls the shared `Globals.skipAnimation`, which makes goals immediate: useful, but a global policy is material when separate embedded workshops coexist. Prefer a deliberate scoped adapter where appropriate and verify hydration and preference toggles. [SSR hook](https://www.react-spring.dev/docs/utilities/use-isomorphic-layout-effect), [reduced motion](https://www.react-spring.dev/docs/utilities/use-reduced-motion).

## GSAP / Flip: credible layout alternative, excluded pending permission

Flip records current geometry, then animates offsets after DOM/style changes. It is a real layout-transition candidate, and `useGSAP` supplies context cleanup for React. A Flip duration/easing animation is not evidence of velocity-preserving spring retargeting. [Flip reference](https://gsap.com/docs/v3/Plugins/Flip/), [React lifecycle guide](https://gsap.com/resources/React/).

The current GSAP license prohibits certain tools that enable visual animation creation competing with Webflow without prior written consent. Its FAQ allows AI-generated code and some niche visual tools, so a blanket “all editors prohibited” claim would also be wrong. A public Radiant spring workshop with live visual controls/export has enough overlap that the license does not provide a clear unrestricted foundation. **Exclude from adoption unless Webflow gives written clarification/permission for this exact product**, rather than assuming “free commercial use” answers it. This is an engineering licensing boundary, not a legal ruling. [License definitions, restrictions and FAQ](https://gsap.com/community/standard-license/).

## Additional MIT layout candidates: neither establishes retained momentum

**Anime.js 4.5.0** has a maintained, framework-independent layout API: `createLayout`, explicit `record()`/`animate()`, and `update(callback)` for geometry/DOM mutations. Its update documentation warns that some frameworks need the manual record/animate sequence. Layout accepts `spring()` as an easing, but that spring is a generated curve plus settling duration, with an explicit initial velocity defaulting to zero. [Layout API](https://animejs.com/documentation/layout/), [update lifecycle](https://animejs.com/documentation/layout/layout-methods/update/), [spring generator](https://animejs.com/documentation/easings/spring/).

The exact published `layout/layout.js` records current visual state, cancels the running transform animation and timeline in `record()`, then constructs new animation timing and a new timeline in `animate()`. There is no capture/transfer of old per-axis layout velocity in that module. Fresh spring curves can start from the interrupted visual position, but that does not meet the strict momentum requirement. Providing a fixed `spring({ velocity })` is not an automatic vector velocity mapping when geometry/distance/direction changes. Anime.js therefore remains a credible layout candidate with the **same unproved/absent automatic momentum carry** boundary, not an alternative that passes this requirement. [Published Anime.js 4.5.0 layout source](https://unpkg.com/animejs@4.5.0/dist/modules/layout/layout.js).

**React Flip Toolkit 7.2.4** supplies actual FLIP layout with spring configuration and inverse child transforms. Its public documentation includes interruption callbacks and reduced-motion handling, which are useful but do not assert velocity continuity. [Upstream documentation](https://github.com/aholachek/react-flip-toolkit).

The published `flip-toolkit` 7.2.4 implementation records current rectangles, destroys each entry in `inProgressAnimations`, then constructs a fresh Rebound spring through `createSpring()` and `setEndValue(1)`. The underlying spring class can set velocity, but this FLIP replacement path does not capture/transfer the destroyed spring's velocity into the new spring. Position continuity and use of a physical solver do not establish momentum continuity. Its release age adds a maintenance concern alongside the strict behavior gap. [Exact published Flip Toolkit implementation](https://unpkg.com/flip-toolkit@7.2.4/lib/index.es.js).

## Claims the real-host proof must settle

1. **Retargeting:** change a live numeric target twice before rest; log positions/velocities across the change. Reject a zero-velocity restart or position jump. Include rapid button press/release, pointer cancellation and disabled state.
2. **Layout:** resize disclosure content and change the actual DOM order of a keyed list while moving. Sample visible x/y/width/height over time before and after retargeting, including a target that changes direction. Compare velocity continuity as well as intermediate projected bounds and settled normal-flow bounds; preserve text readability and focus. Reject a zero-velocity restart even when the element does not jump.
3. **Drag / snap:** use real pointer events and bounds; record release velocity, selected snap target and settling. Supply a keyboard alternative. A scripted target change is not a drag proof.
4. **Following:** repeatedly move an independent source; follower must continue toward its latest value without stale queued targets or per-frame React state updates.
5. **Native hosts:** exercise Radiant button activation, native details/summary toggle and native dialog `showModal()`/Escape/focus restoration. Keep semantic close immediate; cancel/reset visual spring work on close. Entry plus native dismissal is a narrower proof than full exit presence.
6. **Reduced motion / SSR:** render before a browser exists, hydrate without mismatch, then toggle the preference while motion is active. Goals/semantic actions must complete, no infinite frame work, no motion flash needed to reach useful UI.
7. **Loading:** bundle a no-motion consumer and an opt-in candidate using the same bundler/minification settings; record raw/gzip and imported modules, including transitive packages. Measure interaction/lazy chunks separately. No engine should enter Radiant's ordinary root/stylesheet path merely because the workshop uses it.

**No reviewed complete approach passes the strict combined contract yet.** Motion's numeric `springValue` can remain a promising physics core, but Motion's integrated layout must not be marked passing retained-momentum layout. Anime.js and React Flip Toolkit do not close that gap; React Spring would require a layout adapter. Keep serialized spring parameters independent of runtime objects, and defer the stable public adapter/API until the host proof and loading evidence exist.

The product decision is explicit: either accept Motion's position-continuous layout with velocity reset as a documented relaxation, or authorize a **Radiant-owned geometry/scheduling adapter over an upstream physics core such as Motion `springValue`**. The latter reuses the solver but makes Radiant responsible for coordinate changes, retained per-axis velocity, resize/reorder measurement, parent/child projection, transform ownership and cancellation. It needs its own bounded design/proof; it is not merely a thin interface to the existing layout engine. Until that decision and proof, downstream spring milestones remain gated rather than silently dropping momentum-aware layout.

## Native lifecycle and transform ownership boundaries

Native details visibility follows `open`; summary activation changes that state, and grouped details may close each other. Native dialog close removes `open`, updates modal/top-layer state and performs focus restoration under the standard's conditions. An animation adapter should observe those transitions rather than cancel default activation or delay `.close()` until a spring rests. Test Escape, close buttons, `method="dialog"`, rapid reopen and cleanup while moving. Do not claim focus restoration unconditionally when the prior focused element is gone. [HTML details and dialog algorithms](https://html.spec.whatwg.org/multipage/interactive-elements.html).

A closed details content slot has hidden content visibility. Animating its descendants does not alone keep them visible on exit. Chrome's native CSS path targets `::details-content` with a discrete `content-visibility` transition; animating to intrinsic height adds separate `interpolate-size`/`calc-size()` support requirements. This is progressive browser machinery, not automatic spring-layout coverage. An entry/resize proof may preserve immediate native collapse and explicitly leave full visible collapse exit unproved. [Chrome details guidance](https://developer.chrome.com/blog/styling-details).

For dialog visual exit, CSS can transition `display` and `overlay` with `allow-discrete`, and use `@starting-style` for entry; `overlay` lets the browser defer visual top-layer removal during that transition. This can coexist with immediate semantic `.close()`, but requires its own cancellation, rapid-reopen, focus, backdrop and browser-fallback tests. It is not supplied merely by keeping a React node mounted with `AnimatePresence`. [Chrome native entry/exit guide](https://developer.chrome.com/blog/entry-exit-animations/).

The exact `framer-motion` and `motion-dom` 14.7.1 published ESM modules were inspected in memory from their registry tarballs. A string audit found no `HTMLDialogElement`, `showModal`, `allow-discrete` or `overlay` implementation; the official Motion layout example's `<motion.dialog>` therefore is not evidence of native `showModal()`/close retention. This limited source observation does not prove every possible CSS composition unsupported. **The current host proof should claim entry plus immediate native dismissal, not full spring-driven top-layer exit.** [Published Framer Motion archive](https://registry.npmjs.org/framer-motion/-/framer-motion-14.7.1.tgz), [published Motion DOM archive](https://registry.npmjs.org/motion-dom/-/motion-dom-14.7.1.tgz).

Transform ownership needs an explicit seam. The published Motion DOM `render/html/utils/build-styles.mjs` builds an inline `transform` from independent Motion values; `projection/node/create-projection-node.mjs` writes `targetStyle.transform` and, in reset paths without a template, `none`. Arbitrary caller CSS transforms are consequently not guaranteed to survive same-host projection. `transformTemplate` is a documented composition hook, but a fixed prefix cannot automatically reproduce arbitrary dynamic stylesheet/caller transforms or all projection measurement cases. [Versioned build styles](https://unpkg.com/motion-dom@14.7.1/dist/es/render/html/utils/build-styles.mjs), [versioned projection source](https://unpkg.com/motion-dom@14.7.1/dist/es/projection/node/create-projection-node.mjs), [transform template contract](https://motion.dev/docs/react-motion-component#transformtemplate).

For a button press or dialog entry, an adapter can instead subscribe to a raw spring and write the native individual **`style.scale`** property, leaving `style.transform` untouched. CSS composes individual translate/rotate/scale and the transform list in a specified order; this preserves the transform property, not an arbitrary caller's simultaneous scale ownership. Save/restore the prior scale, document that reserved property, and test a caller rotation/translation during and after animation. For layout projection, prefer an explicit dedicated motion part/wrapper with engine-owned transform; preserve semantics on the native host and inspect changed containing blocks, clipping, focus rings and table/list structure. [CSS individual-transform model](https://drafts.csswg.org/css-transforms-2/#individual-transforms).

## Accepted decision — 2026-10-27

The owner accepted Motion with a Radiant-owned layout adapter. This resolves the
architecture gate without relaxing retained momentum. The bounded real-host proof
uses persistent Motion spring values for measured local x/y/width/height; it
checks continued travel after reversing both actual DOM reorder and resize.
Production runtime is DEV-172; full layout measurement/integration remains
DEV-177. Motion projection is not the selected layout path. See the
[accepted ADR](../adr/0001-spring-engine-boundaries.md).
